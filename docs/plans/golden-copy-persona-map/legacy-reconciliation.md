## What this says about lineage

The school application was a separate product line with concrete education-shaped routes and backend modules. The inspected backend `main` explicitly characterized itself as a prototype; later workflow additions live on `origin/workflow-educ`, so backend main and branch state must remain distinct in any history view. The frontend contains routes for student, teacher, admin and super-admin journeys, but routes alone do not establish production maturity or matching backend integration.

The SaaS line had payment and paywall behavior removed in August in favor of contract entitlements. A later self-serve authentication implementation exists on an Enterprise backend branch, but is outside the Golden Copy backend main ancestry. Do not describe it as ported into the current monorepo. In particular, an edition assignment and an origin label answer different questions: “where did this come from?” versus “where is it available now?”

## Reconciliation and process improvements

1. Keep origin, implementation status, current feature key, and proposed edition assignment as separate fields. Never derive an edition from the repository name or the commit authoring context.
2. Maintain a history ledger like this beside the current feature inventory. Each row should cite repository, immutable commit/ref, source path, classification, and current equivalent (or explicitly `none identified`). Distinguish `integrated`, `branch-only`, `prototype-only`, `replaced`, `retired` (only with explicit removal/deprecation evidence), and `absent-from-current`.
3. Before assigning a legacy feature to a current edition, reconcile the user journey end to end: UI route, API boundary, persistence/provider, authorization, and deployment composition. A similarly named catalog entry is only a candidate mapping.
4. Add a merge/import reconciliation checklist for product-line work: enumerate source branches and old repositories, record merged/unmerged refs, map source paths to current paths, identify behavior intentionally omitted, and require a named disposition for each journey.
5. Keep school workflow recovery separate from the current entitlement proposal. The current EDU placeholders (`identity.lms-lti`, `identity.cohort-policy`, `identity.edu-provisioning`, `identity.ferpa-workflows`) are not evidence that the historical education product was ported.
6. Add a decision record before changing assignments for shared behaviors such as QA. Split capabilities only where independent enforcement, configuration, tests, and support boundaries exist; retain a shared baseline where all editions need the same behavior.

This ledger is historical evidence and a set of process recommendations. It does not decide which legacy journeys should be revived or which edition should receive them.
