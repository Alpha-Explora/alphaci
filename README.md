# AlphaCI

The AlphaCI platform in one repository: an npm workspaces monorepo run with
[Turborepo](https://turborepo.com).

| Path | Workspace | What it is |
|------|-----------|------------|
| `apps/api` | `@alphaci/api` | NestJS backend. Owns the product catalog, GitHub integration and migrations. |
| `apps/web` | `@alphaci/web` | Next.js frontend. |
| `packages/capability-catalog` | `@alphaci/capability-catalog` | Capability keys, maturity, pack applicability and dependencies. Generated by the API (`npm run package:capability-catalog -w @alphaci/api`), consumed by the web app. |
| `packages/api-contracts` | `@alphaci/api-contracts` | HTTP wire types (request and response shapes) shared by both apps. Types only: no build step, nothing loaded at runtime. See [its README](packages/api-contracts/README.md). |
| `packages/config` | `@alphaci/config` | Configuration both apps share: `tsconfig.base.json` (compiler options both set identically) and `oxlint.base.json` (Oxlint rules both enforce identically). Each app extends them. No build step. |
| `deploy/selfhost` | — | The self-hosted appliance bundle (Docker Compose, Caddy, `alphaci-ctl`) that runs both images. Customers install this folder. |

The reusable GitHub Actions workflows that generated customer pipelines call
stay in their own public repository,
[`Alpha-Explora/alphaci-workflow`](https://github.com/Alpha-Explora/alphaci-workflow).
Customer pipelines reference it by name (`uses: Alpha-Explora/alphaci-workflow/.github/workflows/<file>.yml@v1`),
so it cannot move into this repository.

History: `apps/api` and `apps/web` were imported with their full history from
`Alpha-Explora/alphaci-golden-copy-be` and `Alpha-Explora/alphaci-golden-copy-fe`.

## Getting started

Node 24 (`.nvmrc`) and npm. Always install from the repository root; there is
one lockfile, `package-lock.json`.

```bash
npm install
npm run build        # turbo run build      (both apps)
npm run typecheck    # turbo run typecheck
npm run lint         # turbo run lint
npm test             # turbo run test
```

Run one app's scripts with `-w`, or from its folder:

```bash
npm run start:dev -w @alphaci/api     # API on :4000
npm run dev -w @alphaci/web           # web on :3000
npx turbo run test --filter=@alphaci/web
```

Each app keeps its own scripts, checks and docs; see
[`apps/api/README.md`](apps/api/README.md) and
[`apps/web/CLAUDE.md`](apps/web/CLAUDE.md).

## Dependencies

npm workspaces hoist shared dependencies to the root `node_modules`. Where a
package needs a different major version, npm installs that copy under the
app's own `node_modules`. Add a dependency to one app with
`npm install <pkg> -w @alphaci/api`.

A dependency listed by more than one `package.json` (the root's included) must
use the same version range in each. `npm run check:versions`
(`scripts/check-versions.mjs`) fails otherwise, and CI runs it on every pull
request. When two ranges must differ on purpose, add the dependency to
`ALLOWED_DIFFERENCES` in that script with the reason.

### Lint and typecheck toolchain

- **Two TypeScripts.** `typescript` is 6.x: ts-jest, typescript-eslint, Nest's
  emit (`npm run build`), `next build` and dependency-cruiser import its API,
  which TypeScript 7 does not have yet (planned for 7.1). TypeScript 7, the
  Go compiler, is installed as `typescript-7` and only checks: each
  `typecheck` script runs `node ../../node_modules/typescript-7/bin/tsc
  --noEmit`. Both packages ship a `tsc` binary, so `node_modules/.bin/tsc` may
  be either one; scripts call each compiler by path.
- **Oxlint, then ESLint.** `npm run lint` runs Oxlint first (`.oxlintrc.json`
  in each app; type-aware rules through `oxlint-tsgolint`, which uses
  TypeScript 7), then ESLint for the few rules Oxlint lacks.
  `eslint-plugin-oxlint` turns off in ESLint every rule `.oxlintrc.json`
  runs, so no rule runs twice. To add or change a rule, put it in
  `.oxlintrc.json` if Oxlint has it (`npx oxlint --rules`), otherwise in
  `eslint.config.mjs`.
- **Shared config.** `packages/config` (`@alphaci/config`, a devDependency
  of both apps) holds only what both apps already set identically. Each
  app's `tsconfig.json` extends `@alphaci/config/tsconfig.base.json` and
  keeps its own module system, target, decorators or JSX, paths and types.
  Each `.oxlintrc.json` extends `oxlint.base.json` (the rules both apps
  enforce with the same settings) and keeps its own plugins, categories, env,
  overrides and the rules only it runs; `eslint-plugin-oxlint` follows
  `extends`, so ESLint turns the shared rules off too. Move a setting there
  only when both apps agree on it. Prettier is the API's alone
  (`apps/api/.prettierrc`); the web app does not use it. A change under
  `packages/config` marks both apps affected in CI.

`allowScripts` in the root `package.json` lists which install scripts npm may
run.

### Security overrides

npm honours `overrides` only in the root `package.json`. Today it forces
`exceljs`'s `uuid` to `^11.1.1` (GHSA-w5hq-g745-h8pq); the QA report workbook
specs cover that path. Known and accepted (moderate, reviewed 2026-11-02):
`minimatch` < 11.0.1 (GHSA-g3hv-75wg-m249) has no patched release below 11; in
production it is reached only through `exceljs` → `archiver` → `readdir-glob`
with patterns from our own code, never user input. The other `npm audit`
findings (`glob` 9–14.0.1, `deepmerge`) are dev tooling only (ESLint, Jest).

## Git hooks

`npm install` installs a pre-push hook ([lefthook](https://lefthook.dev),
`lefthook.yml`). In parallel, it typechecks the apps a push touches (unchanged
apps replay from the turbo cache) and lints the pushed files of each app:
Oxlint (2-3 s), then ESLint (5-7 s for a handful of files). A push that
touches no app source skips the lint step. Most pushes pass in about ten
seconds. Skip once with `git push --no-verify`.

## CI

`.github/workflows/ci.yml` is the whole pipeline:

- **`plan`** installs dependencies once (cached; pushes to `main` keep the
  cache warm for pull requests) and decides which apps a pull request affects
  with `.github/scripts/plan-affected.sh`. Changes to `deploy/`, workflows or
  root workspace files run everything. It also runs `npm run check:versions`.
- **`API …` and `Web …` jobs** run one slice of an app's checks each, in
  parallel: lint, typecheck, tests, architecture and documentation checks,
  the API end-to-end suite, and one job per web profile build. A job whose app
  was not affected is skipped.
- **`Full-stack e2e`** runs when either app is affected. It starts Postgres,
  the compiled API in self-hosted mode and the built web app, then drives
  Playwright journeys against the real API, with every provider switched off
  and outbound requests refused. Run it locally with
  `npm run test:fullstack -w @alphaci/web` (needs Docker). On failure the job
  uploads `apps/web/test-results/fullstack/` as `fullstack-e2e-report`.
- **`Affected detection guard`** replays synthetic changes through
  `plan-affected.sh` so a detection bug fails CI instead of skipping work.
- **`ci-passed`** fails if any job failed or was cancelled. It is the only
  required check.

Pushes to `main`, the nightly run (04:00 Manila) and manual runs check every
app. Run the same slices locally with
`npx turbo run lint typecheck test --filter=@alphaci/web`.

`onprem-agent-release.yml` publishes the on-prem agent installer on
`onprem-agent-v*` tags.

## Docker images

Both Dockerfiles build from the repository root and use `turbo prune` to cut
the context down to one app:

```bash
docker build -f apps/api/Dockerfile --build-arg TEMPLATE_CLONE_TOKEN=... -t alphaci-be .
docker build -f apps/web/Dockerfile --build-arg NEXT_PUBLIC_API_BASE_URL=/api/v1 \
  --build-arg ALPHACI_BUILD_PROFILE=enterprise --build-arg ALPHACI_EDITION=enterprise -t alphaci-fe .
```

Releases: pushing a `v<version>` tag runs `.github/workflows/release.yml`,
which pushes both images to GHCR (`alphaci-be`, `alphaci-fe`) with provenance
and an SBOM and publishes a GitHub Release listing both digests. Pull requests
that touch the Dockerfiles or the lockfile build both images without pushing.

## Deployments

- **API on Render**: `render.yaml` (outbox cron) builds `apps/api/Dockerfile`
  from the root. The web service needs the same settings: Dockerfile path
  `apps/api/Dockerfile`, Docker build context `.`.
- **Web on Vercel**: set the project's Root Directory to `apps/web`. Vercel
  installs from the workspace root automatically.
